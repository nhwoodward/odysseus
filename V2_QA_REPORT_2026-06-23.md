## 2. 🚩 BROKEN in production — Gallery image editor (v2 only)

**Severity: P1 (headline feature broken on v2, works on OG).**

- v2 reuses the original 3,800-line canvas editor inside an iframe at `/v2/gallery-editor-frame`.
- Live: creating a canvas loads the iframe (`/v2/gallery-editor-frame?size=1024x1024`, 780×527), but the browser **blocks it**:
  ```
  Framing 'https://archlinux.tail153f41.ts.net/' violates CSP directive "frame-ancestors 'none'". Blocked.
  ```
- Confirmed via curl: **every** page (`/`, `/v2`, `/v2/gallery-editor-frame`) returns `Content-Security-Policy: … frame-ancestors 'none'` — so no page can be framed, including the editor frame v2 explicitly embeds.
- **Root cause = stale deploy, not a code bug.** Source at HEAD (`core/middleware.py:129-141`, landed in commit **c1ac1eb**) correctly sets `frame-ancestors 'self'` + `font-src 'self' data:` for `is_gallery_editor_frame`, and the default branch (`:155-165`) adds `data:` to `font-src`. The **deployed Docker image returns the pre-fix CSP** (`frame-ancestors 'none'`, `font-src` without `data:`) → the backend image was never rebuilt with the fix. (Frontend bundle is current via `docker cp` hotfix; backend is stale.)
- **Fix:** rebuild the backend image — `docker compose up -d --build odysseus` — so the CSP middleware fix ships. (This also fixes §3.)
- OG is unaffected because it loads the editor natively (`static/js/galleryEditor.js`), not via iframe.

## 3. CSP font-src misconfiguration (cosmetic, same root cause as §2)

Every v2 route logs:
```
Loading the font 'data:font/woff2;base64,…' violates CSP directive "font-src 'self' https://cdn.jsdelivr.net". Blocked.
```
The v2 bundle inlines a small woff2 as a base64 data-URI; the **deployed** CSP omits `data:` from `font-src` (source HEAD already includes it). Fonts fall back, so it's visual-only — but it's a console error on every v2 page. Fixed by the same rebuild as §2.

## 4. Cookbook 403 polling storm (non-admin, shared OG + v2 — pre-existing)

- Cookbook endpoints (`/api/cookbook/state`, `/api/cookbook/tasks/status`, `/api/cookbook/gpus`, `/api/model/cached`) are admin-gated (`require_admin`, `cookbook_routes.py:2106` etc.) → `403` for this non-admin user.
- **Both OG and v2 poll these endpoints on a timer and retry indefinitely on 403** — 10–15+ `403` console errors within seconds on both apps. The page doesn't crash (v2 still renders the public hwfit "Discover & Fit" catalog with the live hardware probe: AMD GPU card0 ×1, 1 GB VRAM, 61.4 GB RAM), but the poller never backs off / stops on 403.
- **Not a v2 regression** — OG does the same. A shared UX/waste issue: the cookbook poller should stop (or the Cookbook nav should hide) for non-admins. v2 polls `tasks/status` more aggressively than OG.
- Also a **medium backend/frontend contract mismatch** (workflow): `web/src/api/cookbook.ts:159` narrows the diagnosis object to `{message?}`, silently discarding the backend's structured `suggestions` array (`cookbook_routes.py:94-128`) — root cause of the "auto-diagnose serve crashes / auto-fix buttons" gap. Backend is correct; the v2 client drops data.
